# 纪要内容与阅读结构优化

## 参考材料带来的调整

对照同一会议的校对稿、旧版纪要和用户提供的 Word 范本，主要问题不是概览不够短，而是正文缺少主题层次、具体方案被挤在长条目中，以及逐字校对疑点淹没了有效信息。

新版借鉴范本的主题组织方式，保留原文约束。范本只用于设计写作方式，不会作为会议事实、人员映射或指令传给模型。例如，原话“两三段话”不能改成“两三页 PPT”，转述和建议不能升级为已确认要求。

## 生成流程

一次总结请求内完成四步整理，不增加额外模型调用：

1. 通读并建立主题与原文证据的对应关系，合并跨时间的相关讨论，保留后续澄清。
2. 按主题展开细节，分别描述方案各层、客户类型、角色需求、现有进展、能力缺口与分工；只覆盖实际讨论的内容。
3. 核对事实状态、决策、任务、责任人、数量、材料形式与时间，避免把建议或转述写成定论。
4. 精简口头语和重复提示，将关键限制与逐字校对详情分开。

上述四步是生成指令，不是可独立验证的模型内部步骤。代码仍对每条引用做逐字验证、核查责任人与日期，并保留不确定决策的处理。引用有效只能证明文字来自输入，不能保证归纳的语义完全正确，因此仍需样例质量检查。

## 数据与展示

- `MinutesPoint.heading` 是可选主题小标题。连续相同标题只显示一次，每个条目仍保留独立引用。App 与 Markdown/TXT 导出均支持。
- `MeetingMinutes.limitations` 保存模型归纳的关键限制及验证器提示，不再自动拼接整个校对日志。提示要求通常 0–3 条、最多 5 条；此数量是写作要求，程序不会为满足数量而截掉内容。
- `MeetingMinutes.reviewDetails` 完整保存输入中的录音与校对详情，在 App 中默认折叠。常规纪要导出保留关键限制与逐条原文依据，完整日志仍在校对稿和输入快照中。
- 术语表也传入总结请求，作为理解背景，与原话证据分开，不能据此补造事实或确认人名。
- 内置会议模板升至 V2。旧设置在下次生成时解析为新版内置模板；历史纪要继续使用生成时的模板快照。自定义模板不升级。
- 新字段可选，旧纪要、人工编辑版以及原校对流程兼容保留。

## 验证方法

`bash scripts/test.sh` 覆盖主题与引用的保存/导出、校对日志隔离、旧数据读取、内置模板升级、自定义模板保留，以及原有引用、决策、责任人和日期约束。

可以用脱离会议数据库的预览入口验证真实样例：

```sh
MeetingAIValidate --preview-summary PROFILE REGION INPUT_SNAPSHOT_JSON OUTPUT_MD
```

输入为 `AIInputSnapshot` 的 JSON，调用与 App 相同的总结入口；输出 Markdown 及同名 JSON 版本收据。该命令会将输入发送到配置的 Bedrock 模型，不写入会议数据库、不重做校对。私人样例放在已忽略的 `dist/summary-quality/`，不提交为测试素材。

样例人工检查应覆盖：各层能力有没有具体内容；客户类型与角色是否分开；治理缺口和已有资产是否遗漏；分工是否逐项清晰；后文的范围澄清是否保留；是否把试探性安排写成确定交付；疑点是否仅限定相关内容。模拟测试不替代这一步。
